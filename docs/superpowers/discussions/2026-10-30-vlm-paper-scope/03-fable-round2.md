## 2. 坚持（与 Opus 仍有分歧）

### 2.1 主板阻挡规则不是「V7-motherboard 要不要」的问题，是 V4 / V6 真值的问题

Opus 把「drive_cage / optical_drive / psu / cover → motherboard 的类级裁定」列为 V7-motherboard 的前置。我认为它是**全部可供性任务**的前置：今天的图在硬盘架压着主板时判「remove motherboard 合法」，那么 V4 的「图允许」上界、V6 的合法集合、V16 的「候选序列是否合法」在这 43 台上都带着同一个错，不只是 V7。Opus 自己的主线「只用确定真值」里，V4 正例 = 演示过的、反例 = 图挡住的，这两类确实不受影响；但 V6 的「合法率」和 V16 的「程序生成的错误序列」会受影响（一个先拆主板再拆硬盘架的序列今天被判合法）。所以这 1 小时裁定**必须做**，而且要在冻结评测集之前。

### 2.2 怎么把裁定变成边：类对白名单 + 像素实例化（新提案，请 Opus 挑刺）

两件散热器那 8 台的「硬盘架 / 光驱压散热块」和 43 台的「硬盘架 / 光驱 / PSU / 导风罩压主板」是同一类问题：**刚性大件压在别的零件上**。写成每台的边违反「不做每台的特例」；写成无条件的类级规则（「硬盘架总是压主板」）在没有重叠的机器上是假的。提案：

- 用户裁定一张**类对白名单**：`(above_class, below_class)` 里「盖住即阻挡」成立的对，候选只从 r2b 候选榜前 15 个类对里挑，限刚性大件为 above：drive_cage、optical_drive、psu、cover（导风罩 / 挡板）、cpu_cooler、expansion_card；below 不限。线缆、接头、螺丝不进 above。
- 规则：对白名单里的类对，若该台**已确认帧**上 `covers.max_px ≥ 阈值`（如 2 000 px，或 below 完整形状的 10 %），则生成 `covered_by(below ← above)`，`source = pixels`，`evidence_step` 记首次观察到的帧，必要性 required。
- 这样边仍是「规则 + 证据」推出的，可重跑、可解释、不含每台手写；和现有 `covered_by` 同一语义（挡全部动词，接受 open / removed / displaced）。
- 风险：像素覆盖 ≠ 物理阻挡（导风罩盖住主板不一定挡住主板取出；PSU 悬在主板上方未必阻挡）。所以白名单要用户逐对判断，而不是看像素就算；而且只在确认帧上算，未确认的台不生成。
- 验证：加规则后 `constraints --dry-run --validate` 违规数不升（日志里这些大件都先拆，预期 0 新违规）；重跑 export-graph 看 43 台的主板计划不再穿过阻挡件、8 台的 CPU 计划长度合理。

### 2.3 Review 遮挡口述：不是「推迟到投稿后」一句话能了的

Opus 建议口述整体推迟、卡扣 / 压杆在 L1 结果里单列并注明层级问题。我同意 66 台口述放不下，但要把后果说清：HANDOFF §4.2 的系统性反序（压杆 57/57、内存卡扣 714/724 在被扣零件之下）意味着**发布的扫描仪可见掩码里，这两类小件的可见部分是错的**（本该露出的被扣零件盖住）。这是数据集本身的缺陷，不只是 V8b / V20 做不做。三个选项，用户定：
- (a) U41 的全局抬升（只抬压杆 / 卡扣一项）+ 用户裁决演练里出现的 983 个冲突（502 帧）——要先量一下用冲突面板裁 983 个要多久，我估 4–6 小时，这是用户时间；
- (b) 不改，数据卡和论文局限明写「latch / lever 层级在 v1.0 已知偏差，v1.1 修」，L1 表里这两类单列；
- (c) 只在测试机上口述 + 修（约 12 台，每台 40 帧左右看一遍），训练侧按 (b) 处理。
我倾向 (b) 或 (c)，取决于 (a) 的实测时间。

### 2.4 多视角：零样本不依赖划分，但 V15 的样本要来自有掩码的视角对

同意 Opus「子集不必落在测试机」。补一条：V15「A 视角被挡的 X 在 B 视角是什么状态」要两边都有可见性标签，所以 3 台试点必须两个视角都确认，不是「3 台 × 1 个视角」——1 个视角只能做 V14 的另一视角版本。先做 1 小时的不一致率测量（D13 / D24 / D33 的 LS 草稿），再决定做不做；我把这项放在控制方的时间里，不占用户。
