## 1. §2.1 主板阻挡规则：**做，第 3 天前做——这点一致；但它不是 V4 / V6 / V16 真值的前提**

我查了生成器，三个任务都不会因为图漏边而出错误标签：

- **V16**：`gen_v16` 的有效计划**只有日志后缀**（docstring 原话：「a rearrangement the graph happens to permit is not known to work」）；无效计划只在篡改后**违反现有必要边**时才出，「什么都不违反的篡改」直接不出。所以「先拆主板再拆硬盘架」这种序列今天**不会**被标成合法——它根本不会作为有效样本出现。
- **V6**：标签 = 演示过的动作 + 确定错的动作（图挡住 / 状态不适用）；「合法率」在代码里已经换成 `blocked_rate`（docstring：「Legal rate was the wrong metric」）。漏边只会让一些物理上做不到的动作落进 `permitted_unknown` 干扰项，而这一类不计为错。
- **V4**：正例是演示过的，反例是图挡住的或状态不适用的，同样不受漏边影响。

漏边真正影响的是三样东西：（1）V7 的计划评分；（2）**发布的 export-graph JSON** 里的 `legal_by_step` 和 `plans`——那里直接写着「remove motherboard 合法」，这是对外的错误陈述；（3）难负样本的覆盖面：边少，确定错的选项就少。

反过来还有一点：**每加一条边，就多一批「确定错」的反例**（V4 反例、V6 错误选项、V16 篡改）。白名单边会变成真值来源，所以它的**精确率比召回率重要**。建议这批边在样本里单独标 `truth_source = graph_blocked_pixels`，表里可以单列，也可以做去掉它们的消融。

结论：动作一致（第 3 天前裁定并上线）；理由我改写成「发布正确性 + V7 + 负样本覆盖」，不是「真值前提」。所以万一延误，评测集照样可以按时冻结，只是 V7-motherboard 不进论文、graph JSON 晚一点发布。

## 2. §2.2 类对白名单 + 像素实例化：**同意机制，有五处修改**

### 2.1 会不会制造违规——不会，但这句话证明不了什么

p13：在 above ∈ {drive_cage, optical_drive, psu, cover, cpu_cooler, expansion_card}、正反向都没有边、也没有结构理由的遮挡对上，检查日志第一次对下面零件动手时，上面零件是否已经 open / removed / displaced：

| 类对 | ≥500 px（对数 / 违规） | ≥2000 px | ≥5000 px | ≥下面零件 10 % |
|---|---|---|---|---|
| cpu_cooler → cpu_socket_lever | 64 / 0 | 64 / 0 | 64 / 0 | 64 / 0 |
| cover → motherboard | 56 / 0 | 47 / 0 | 34 / 0 | 22 / 0 |
| expansion_card → motherboard | 35 / 0 | 35 / 0 | 31 / 0 | **0** / 0 |
| drive_cage → motherboard | 34 / 0 | 33 / 0 | 33 / 0 | 21 / 0 |
| optical_drive → motherboard | 22 / 0 | 22 / 0 | 22 / 0 | 19 / 0 |
| optical_drive → storage_drive | 20 / 0 | 20 / 0 | 20 / 0 | 20 / 0 |
| drive_cage → ram_module | 31 / 0 | 18 / 0 | 5 / 0 | 31 / 0 |
| psu → motherboard | 11 / 0 | 10 / 0 | 10 / 0 | **0** / 0 |
| drive_cage / optical → cpu、heatsink、拉杆（8 台） | 各 8 / 0 | 各 8 / 0 | | |
| drive_cage → connector | 64 / 0 | 8 / 0 | 0 | **109** / 0 |

所有阈值下合计，违规只有 7 个对（≥2000 px），全在**不会进白名单**的类对上：cpu_cooler → cooler_latch（D04、D05，第 2 步就拆了卡扣）、expansion_card → cover（D29、D32）、cover → cover（D49、D62）、psu → cover（D62）。

但「0 违规」几乎是被构造出来的：
- 操作员总是先拆上面的大件；
- 更要紧的是，**层级的方向本身就来自拆卸顺序**。标注是倒序画的，U17 的默认规则是「新画的在上」。拆得越早的零件，倒序里越晚画，所以默认就在上面。`pair_override` 0 行，8 410 对里 8 401 对的方向来自 `zorder`，Review 口述也还没开始。

所以「A 盖住 B」里，**重叠面积是真几何，方向在很大程度上是日志顺序的先验**。论文不能说这些边是「从图像观察到的」。准确的说法是：「类级规则（人裁定）× 本机标注里存在重叠（几何）」。下面零件是主板时问题最小：主板是地板层，方向是强制的，物理上也对。

### 2.2 阈值：单一像素数不行，要按下面零件的大小走

p14：主板完整形状中位约 35.2 万 px（最小 28.4 万）；`screw.motherboard` 中位 287 px；内存条俯视约 1 700–2 000 px。

- **大件压主板是双峰分布**，阈值落在 2 000–15 000 之间结果都一样：drive_cage → motherboard 除 D28 的 788 px 外全是 1.66 万+；psu → motherboard 是 3 px、1 171 px，然后 1.65 万+；optical 全是 1.5 万+。
- **「10 % 的下面零件」对主板是错的**：会把 PSU 全部删掉（4.9–6.2 %），expansion_card → motherboard 也全部删掉（0.7–3.7 %）。
- **2 000 px 对螺丝、接头永远不触发**；而用 10 % 时，drive_cage → connector 会从 8 个涨到 109 个，几乎全是边缘噪声量级的重叠。
- **cover → motherboard 是连续分布**（39、65、593 … 2 172、2 415、2 627 … 直到 HP 导风罩的 4–5 万 px），没有自然断点。Dell 机器上是导风罩边沿的几百到两千像素，任何阈值都是随意切。

建议：
- 阈值写成 `px ≥ max(1 000, 0.03 × amodal(below))`，对小件另设 `px ≥ 0.25 × amodal(below)`。也就是主板约 1 万 px、内存约 500 px、螺丝约 70 px。
- **cover → motherboard 不进白名单**。导风罩是否挡主板取出不是一个类级事实；HP SFF 的大导风罩若要算，用户单独裁定「cover.of = cpu_cooler 且 ≥ 5 %」。
- `expansion_card` 只收 `kind = gpu`。wlan 是装在主板上的小卡，随主板走，覆盖不等于阻挡。
- 螺丝、接头作为 below 时，**这一版先不做**：样本量大，像素又在噪声量级，`tool_access` 的判断应该留给人。

### 2.3 像素覆盖不代表阻挡的地方（给用户裁定时看）

1. **`open` 的铰链件**：HP 硬盘架 / PSU 是翻起来的（`displaced` / `open`），俯视图上翻开后仍和主板重叠。这一点不影响边的正确性（`covered_by` 接受 displaced / open），但翻开以后 covers 还会继续计数，不要把它当「还在挡」。
2. **高度不同的悬空件**：PSU 悬在主板一角上方，主板可能可以斜着抽出来。HP SFF 的 10 台日志都是先动 PSU，没有反例，但这是协议，不是物理。用户判断。
3. **drive_cage → ram_module**：Dell MT 的硬盘架悬在内存插槽上方，内存可能拔得出来。用户判断。
4. **支承关系**：cpu_cooler / cpu / ram → motherboard 已经由支承表排除，不进白名单。
5. **层级反序**：above 只限刚性大件，就避开了压杆 / 卡扣的已知反序。但 D01「拉杆盖住 PSU」这类层级错，如果碰上白名单类对也会生成边。实例化之后应输出一张逐台清单给用户扫一眼（按 p13 的 ≥2 000 px 计数，§2.3 的候选类对全收时约 150–200 条，几分钟）。

### 2.4 和 derive / replay 模型怎么接：**不要放进 `propose_edges`，做成一次性固化的独立来源**

- `propose_edges` 和 `derive_edges` 都写明是**纯函数**，只读实例表 + taxonomy。把像素放进去，`constraints` 就要依赖编译行和确认状态：任何一次 `refreeze`、重画、复核都会悄悄改边和 `graph_version`；某条边消失时，它上面的人工裁定会变成孤儿（`ORPHAN_OF`）；结果还依赖视角（像素来自 scan）和 D63 / D64 这种还没有确认帧的台。规则层也不该反向依赖真值层。
- `derive_edges` 已经有现成的位置：`source` 不是 rule / override / manual 的行算 `imported`，「kept, counted, never touched」，重跑 `constraints` 时**逐字节保留**。`relation.source` 是自由文本，唯一索引是 (desktop, type, target, blocker)。
- 做法：
  1. 在冻结前那份副本上跑一次 export-graph 拿 covers。
  2. 一条独立命令（dry-run 默认，`--apply` 才写，程序关着、先备份、每台一条 op_log）按白名单把边写成 `source = 'pixels:W<规则号>'`、`status = 'accepted'`、`reason` 带像素数和帧数、`evidence_step` 记首帧。
  3. 证据另存一份 JSON（白名单版本、阈值、每条边的像素），随数据发布。
  4. 撤销按 source 前缀整批删，同样记 op。
- 依赖顺序：**D63、D64 要先有确认帧**（r2b 里两台都是 0 个遮挡对），否则这两台得不到像素边，只能不出可供性题。

## 3. §2.3 压杆 / 卡扣系统性反序：**v1.0 走 (b)，投稿后立刻做 (a)；不选 (c)**

**缺陷的量级**（U41 演练，当时 57 台）：452 次移动修正 823 对；新开冲突 983 条 / 502 帧。按类别：ram_latch 473（中位 31 px）、cpu_socket_lever 194（中位 319 px）、cpu 175（中位 227 px）、screw 115（中位 128 px，其中 101 条在 D08 / D09）、connector 20、其他 10；容差内陈旧行 7 580 条（`refreeze` 批量重签，不用人看）。现在已确认的台有 64 台，冲突数大约要乘 1.1，约 1 100 条。

**(a) 的用户时间**：
- 逐条 K / N：每条冲突 10–20 秒，或按帧算每帧约 30 秒 → **3–5.5 小时**，和你估的 4–6 小时一致。
- 如果加一个「按 `zorder_lift` 运行号批量接受冲突」的小工具，用户只需要：分层抽看约 100 条（30 分钟）+ 逐条看螺丝 / 接头那 135 条副作用（30–45 分钟）→ **约 1–1.5 小时**。
- 但这要把 U41 分支（基于 38a4853，落后 main 很多，含 §14 钉子仪式）合进来、新写一个批量写库路径、在线上库上跑、再重导 HF 和评测集。这些都要发生在**第 7 天冻结之前**，因为 V8 / V14 / V1 里卡扣和压杆的可见掩码、可见性会变。1–6 天已经排满了（D63 / D64、裁定、试点、抽审、写作）。

**(c) 被 (a) 支配**：只在测试机上口述 + 修，会让同一个发布版本里测试机和训练机对这两类采用不同标准——恰好在这两类上制造训练 / 测试的标签分布差，坑的是将来的微调者。而且口述比 U41 的机械抬升慢、也不更准。真要碰测试机，就在测试机上跑 U41 抬升（约 12 台、约 200 条冲突、约 1 小时），而不是口述；但这仍然是两套标准，我不推荐。

**推荐**：
- v1.0（投稿版）：数据卡和论文局限明写「cpu_socket_lever / ram_latch 的层级系统性偏低，影响它们与被扣零件重叠处的可见掩码（像素中位 31 / 319），v1.1 统一修正」。L1 表里这两类单列，V14 不对这两类出题。
- 11-17 到 11-23（补充材料那一周）：合并 U41 + 批量接受工具，做 (a)，发布 v1.1；补充材料里报修正前后这两类的 L1 数字。
- 例外：如果第 4 天时 1–3 天的工作都已按时完成，可以把 (a) 提到第 5–6 天。这是唯一能让 v1.0 就干净的窗口，过了第 6 天就不要动。

## 4. §2.4 多视角 / V15：**V15-cross 推到 v1.1；V15-moment 零标注做全四视角**

先澄清一下：我在 02 里说的「3 台 × 1 个视角」本来就是「扫描仪（已确认）+ 一个新视角」，两个视角都确认，满足 `gen_v15` 要求 mate 帧 verified 的条件。分歧不在这里，在值不值。

`gen_v15` 有两半：
- **`_v15_cross`**（扫描仪里看不见的零件，在另一视角是什么状态）：需要另一视角**逐实例的可见性**，也就是另一视角要完整标注。3 台（D13 = Optiplex 7020，D24 / D33 = HP SFF，只有两个平台）大约 125 帧 OAK 新视角。没有 OAK 检测器，首次标这个视角，估计 8–12 小时用户时间，得到几百条高度聚类的样本；按台自助法算区间会非常宽，审稿人会把它看成演示，不看成基准。用户剩下的 25–35 小时，同时还要应付 §3 的抉择和写作，这笔投入不划算。**推到 v1.1。**
- **`_v15_moment`**（两张不同视角的图是不是同一时刻）：答案只来自日志状态和帧-步对齐（四台相机由同一次按键触发，index 已经校过），**不需要另一视角的任何掩码**。现在代码要求 mate 帧 verified，只是一个过严的门槛。放开这一条（moment 类只要求帧不缺失、对齐可信），四个视角、66 台全都能出题，不搬任何标签，符合「每视角重新标」的裁定。要注意一点：负样本的帧距 1–3 步时，变化可能只是一颗螺丝，在 RS / OAK2 上看不出来，「不同时刻」就成了不可判定的题。负样本要求两帧之间至少有一个大件（psu、motherboard、drive_cage、optical_drive、cover、cpu_cooler、expansion_card、ram_module）变了状态。工人改动约半天，不占用户时间。

所以：不再需要 1 小时的不一致率测量。那个数只服务于 V15-cross 选哪个视角，留到 v1.1 再量。
