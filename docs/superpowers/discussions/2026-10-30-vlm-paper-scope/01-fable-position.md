## 1. 论文主张以哪一层为主（§6 问 1）

**立场：L2–L4 主打，L1 作地基表而不是标题。** 评测集配比建议 L1 25% / L2 30% / L3 30% / L4 15%，按能力层和推理深度分层报告。

理由：
- 66 台、23 类、单一俯视视角的实例分割，单拎出来在 CVPR 数据集轨道上不够显眼；可验证的「可供性 / 规划 / 拒答」标签是别人没有的，且边际成本接近零（规格 §8.2 的原话）。
- 但 L1 不能缺席：审稿人会要一张「这个数据集上现成模型做得怎样」的分割表；而且 L2–L4 的错误要能和感知错误分离（先问模型看见了什么，再问能不能拆）。
- L4 的 V14（拒答）和 V15（跨视角）在只有扫描仪确认帧的现状下只能部分做（见 §3），所以 L4 比例压低。

代价 / 风险：L2–L3 的真值依赖约束图的完整性；图漏边就会把合法动作判成非法。U46 已把候选对列出来了，§5、§6 两条规则改动就是在补这块。

## 2. V7「剩余计划」的终点（§6 问 2）

**立场：两层目标 + 进度标签。** 主目标 `cpu.01 removed`（65/66 台可达，计划 4–8 步，约束真实：散热器挡拉杆、拉杆锁 CPU）；困难层 `motherboard.01 removed`（60 台，20–40 步，偏序丰富）；`all` 只用来做 V10 的进度分箱，不做计划任务（「全部」由操作员当天拆了什么决定，不是干净的目标）。

理由：短目标让当前 VLM 的差距可测量（长计划人人全错，表上全是 0）；长目标保留给「规划」上限。PSU 61 台但计划很短且几乎与别的零件无约束，不单列。

## 3. 其他三个视角的标注范围（§6 问 3）

**立场：按任务拆开看，不按视角一刀切。**
- **L2–L3 任务可以零成本用全部四个视角的图像**：V3（两帧之间做了什么）、V6（下一步）、V10（进度）、V12（有没有变化）、V16（计划找错）的答案来自日志和状态机，与视角无关，不需要那个视角的掩码。只需一个弱过滤：被问的零件在该视角是否大概率可见，可以用扫描仪的可见性加一条「视角盲区」规则，或者干脆只在不依赖可见性的任务上用。这不违背「每个视角重新画」：没有形状被搬过去。
- **掩码级任务（V1、V8、V14、V15）只在一个多视角子集上做**：子集 = 测试划分里的机器（这样多视角评测恰好落在测试集上），先 OAK1 + RS（视角差最大、RS 带深度），OAK2 看时间。规模按 17 天估：Review 口述要占掉大半标注时间，子集我建议 **6–8 台 × 2 视角**，不多。
- 其余视角的掩码写进论文为 v1.1 滚动发布（数据卡上写清版本），不要在正文承诺 66 台四视角全标。

理由：一个视角重画一遍就是再做一遍扫描仪的工作量，17 天内不可能；而 VLM 侧真正要多视角的地方（V15 跨视角一致性、V14 盲区拒答）用子集就能立起来。

## 5. 推断 `mounted_on`（U46 发现 1）

**立场：做，作为全局类规则，写进 `mounted_on` 列，不碰 `parent`。** 规格 §3 早就定义了 `mounted_on` = 物理支承（RAM→主板、主板→机箱、硬盘→硬盘笼、散热器→主板），只是从来没填。规则草案：
- cpu、ram_module、cpu_cooler、expansion_card、cpu_socket_lever、ram_latch → `motherboard.01`；
- storage_drive 的 kind = m2 / 板载 SSD → `motherboard.01`，其余 storage_drive / optical_drive → 这台的 drive_cage（有且唯一时），否则留空；
- motherboard → chassis.01；psu → chassis.01；cover / 挡板不填（它们是机箱的一部分或自由件）。
- `export-graph` 的 `covers` 把 `(above.mounted_on == below)` 归入 `structural`，不再算候选。

效果：候选 2 411 里的 X→motherboard 大头（cpu 60、ram_module、fan、gpu、ssd、heatsink…）清掉；留下的才是真要看的（drive_cage→screw.motherboard 62、drive_cage→ram_latch、optical_drive→ram_module 等，这些是**遮挡即阻挡**的真候选）。
风险：这是写库的数据改动，走 `infer-relations` 一类的推断路径 + `relation_fix` 记录以便重导保留；先在副本上跑、出差异表给用户过目再上线。它**不**产生约束边（`mounted_on` 不是先后关系），所以不会改变合法集合。

## 6. 散热器 / 风扇 → CPU 拉杆的规则边（U46 发现 2）

**立场：做。** 加硬边 `blocked_by(cpu_socket_lever.N ← cpu_cooler.*)`，必要性 required，来源 rule，条件：同一块主板上（两者 `mounted_on` 或 parent 都指向 motherboard.01；U46 里 fan 38 台、heatsink 18 台的像素证据也支持）。
证据：65/65 台都是先拆散热器再开拉杆，0 台反例 → 新边不会制造违规；现在每台拉杆在第 0 步就「合法可开」，V5 的合法集合里会出现「打开 CPU 拉杆」这种审稿人一眼看穿的荒唐项。
风险：heatsink_fan 4 台要确认 cooler 实例确实压在拉杆上；加边后 `graph_version` 变，已导出的 VLM 样本要重生成（本来就要重生成）。
