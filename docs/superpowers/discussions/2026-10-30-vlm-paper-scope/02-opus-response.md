### §1 论文主打哪一层 —— **部分同意**

同意「L1 不能缺席」和「按层分开报」。反对两点：

**(a) L3 规划不能当主打。** 理由全在图的可信度上：边 100 % 是规则推出、未经人工确认；严格合法率 2 713 / 2 726 看着漂亮，但它不是独立验证——`graph_rules.py` 的 `GATES` 注释里写着，`connected_to` 的门控就是因为「在 66 张表上产生了 34 条违规」才改的。规则是对着演示调过的，演示一致性是**必要**条件，不是图完整的证据。图完整性的反证在 p4：43 台的主板计划穿过了压在主板上 1.5 万到 10 万像素的硬盘架 / 光驱 / PSU。审稿人只要看一个计划例子就会抓住。

**(b) L4 不该因为「只有扫描仪」就压低。** V14（本视角能不能判断 X 的状态）在单视角上就成立：amodal 形状 + `occluded_full` + `viewpoint` / `out_of_view` 标签本来就是按视角给的（D3 扫描仪 1 504 条里 231 条整件被盖住，规格 §8.1）。V14 是这个数据集最独特、最便宜、真值最硬的任务之一。需要多视角的只有 V15。

**我的替代**：主打「**图像里的过程状态**」——状态与计数（V2）、两帧变化（V3、V12）、进度（V10）、可判定性（V14）、可行性（V4，只用确定真值）。这些的答案来自人工校对过的日志 + 状态机 + 人工确认的掩码，是全数据集最硬的真值。规划（V6、V7-cpu、V16）作为第二条线，标题里不承诺「物理正确的规划基准」，而是「图允许的上界 + 图确定禁止的错误率」。

**配比**：不要定 25/30/30/15 这种总配比——除非要报一个总分，配比没有意义，而 CVPR 审稿人更信逐任务的表。按每个任务需要的置信区间定样本数：二分类任务 ≥ 400 条（±5 % @95 %），并且**按台做聚类自助法**算区间（同一台的题高度相关，12 台测试机的有效样本远小于条数）。

**什么能证明我错**：如果在定稿前把主板 / CPU 周围的类级阻挡规则补齐，并且用户抽查 20 个计划都物理上可行，那规划可以升回主线。

### §2 V7 的终点 —— **部分同意（CPU 同意，主板反对）**

01b 的表我在 r2b 上复核过一部分：CPU 计划今天多数 7–8 步，两件散热器的 8 台是 2 步，D45 是 3 步（p3）。

- **CPU 目标：同意**，但要先修两件散热器的边（§6），而且要知道它的「规划」内容很薄：修好后几乎每台都是「[开导风罩] → 拧散热器螺丝 ×4（无序）→ 拿走散热器 → 开拉杆 → 取 CPU」。从第 0 帧问，这是一个通用配方，模型不用看图就会写。**有价值的问法是从中间帧问**（已经拧了两颗螺丝、导风罩已开），这时要看图才知道剩下什么。建议 V7-cpu 只从「CPU 目标进行到一半」的帧出题。
- **两件散热器那 8 台还有第三个缺口**（p12）：硬盘架和光驱压在散热块上（中位 1.9 万 / 2.0 万像素）、压在 CPU 和拉杆上，这 8 台的日志**每台**都先拆光驱（第 9–11 步）和硬盘架（第 11–14 步），再拆风扇（第 14–16 步）、散热块（第 19–27 步）。只加 01b 的两条规则，这 8 台的 CPU 计划仍然会从硬盘架底下把散热块拿走。要么再加一条类级规则，要么这 8 台不出 V7。
- **主板目标：反对放进论文**。p4：66 台里 43 台的主板最短计划结束时，至少一个压在主板上 ≥ 2 000 像素的硬盘架 / 光驱 / PSU / 导风罩 / 机箱风扇还在原位。具体：D02–D21 几乎每台是硬盘架（5.9 万–10 万像素）+ 光驱；D22–D33（HP SFF）是硬盘架 + PSU（1.6 万–2.2 万像素）+ 导风罩。**01b 的 C 段说「差额主要是主板不需要的零件，不是漏边」，数据不支持**：差额里至少有一大块是图漏了的阻挡边。
- **计分口径**：规格 §8.2 V7 的「冗余步数」在图不完整时是**反着**判的——一个正确地先拆硬盘架的计划会被记成冗余。图不完整时只有三个指标是可靠的：（1）是否违反现有的边（图禁止的一定错）；（2）**必需动作召回**：现有边推出的必需动作（螺丝、接头、卡扣）有没有都做；（3）是否达成目标。不要罚多出来的步。

**什么能证明我错**：用户对 `drive_cage / optical_drive / psu / cover → motherboard` 四个类对做一次类级裁定（我估计 30–60 分钟），加规则后重跑 export-graph，主板计划里不再有穿过阻挡件的——那时主板目标可以回来。

### §3 其他三个视角 —— **部分同意，主张更少**

**同意**：不按视角一刀切；不在正文承诺 66 台四视角。

**反对 1：「L2–L3 任务零成本用全部四个视角」只对一部分任务成立。** V6（下一步）、V10（进度）、V16（计划找错）问的是整机状态，换视角答案不变，可以用。**V3（刚做了什么）和 V12（有没有变化）不行**：OAK2 斜视或 RS 1280×720 上，拧下一颗螺丝、拔一个接头在画面里可能完全看不出来，而标签说「有变化 / 拧了 screw.03」。这违反规格 §8.2 原则 5「可见性诚实」——看不见时正确答案是「本视角无法判断」。用扫描仪的可见性做过滤是在搬另一个视角的标签，正是用户 9-19 裁定说的「不能依赖跨视角迁移」（memory `feedback-per-view-annotation`）；也不可靠，因为扫描仪可见不代表 OAK2 可见。替代：V3/V12 在未标视角上只出**大件**的变化（psu、motherboard、drive_cage、optical_drive、cover、cpu_cooler、expansion_card），并在数据卡上写明。

**反对 2：子集的选法。** 立场稿选 OAK1 + RS。但 V14/V15 的价值来自「视角之间可见性不一致」：OAK1 是近俯视，与扫描仪视角最接近，不一致的情况最少；OAK2 斜视才会出现「扫描仪被挡、OAK2 看得见」的题。建议**先花 1 小时量**：D13 / D24 / D33 三台在 OAK1 / OAK2 / RS 上都有 LS 草稿（关键帧 1 751 / 1 210 / 1 702），按实例数一下每个视角与扫描仪的可见性不一致率，选不一致率最高的视角。

**反对 3：规模。** 6–8 台 × 2 视角，同时还有 Review 口述，在 17 天里放不下（见第 3 节预算）。我主张 **0 台或 3 台**：要么正文不放 V15，把它写成 v1.1；要么只做 D13 / D24 / D33 × 一个视角（有草稿，最便宜），把 V15 作为小规模试点，表里单列并注明 3 台。注意这 3 台和测试划分的关系：零样本评测不依赖划分（模型没在任何一台上训练过），所以多视角子集**不必**落在测试集里。立场稿把「子集 = 测试机」当成约束，其实只有微调才需要它。

### §7 评测计划 —— **大方向同意（只做零样本），细节有六处要改**

1. **纯文本基线必须拆成三个，而且不能叫「基线」混在一张表里。** 立场稿的「只给日志不给图」不是盲基线，是**特权状态上界**：日志直接给出了已经拆了什么。我在副本上量了一下协议的可预测性（p7，留一台交叉验证）：只用「上一步的（动词，类别）」预测下一步的（动词，类别），准确率 **71.8 %**；「重复上一步的（动词，类别）」就有 **59.9 %**；总是猜「disconnect connector」36.4 %。所以给了日志的文本模型在 V6 上会很强，而它测的是「会不会接着拧下一颗螺丝」。建议三行：（i）**盲文本**：只给题面和选项，量模板泄露（导出里 `vlm_shortcuts` 已经给了样本内上界）；（ii）**协议先验**：上面那个二元模型，作为 V6 的「不看图也能到哪」参考线；（iii）**状态 oracle**：给结构化状态不给图，作为「感知完美时推理能到哪」的上界——这一行和 VLM 的差就是「感知瓶颈」，是很好的分析图。
2. **V6 的匹配口径**：p8 显示 60.7 % 的步里，和演示动作「同动词同类别」的合法动作不止一个（中位 2、平均 2.9），比如 4 颗无序的散热器螺丝。模型说「拧 screw.cpu_cooler.03」而操作员拧的是 .04，按实例精确匹配就算错——这是标签噪声，不是能力。建议：同一 `group_id`（unordered）或同动词同类别的合法动作都算匹配；精确匹配作为副指标。同时确认 V6 的 `permitted_unknown` 干扰项里有没有这种兄弟件（代码按动词匹配干扰项，很可能有），有的话要从干扰项里剔掉。
3. **V5 建议砍掉**：每步合法集合中位 37 个、p90 57 个、最多 76 个（p8），而且是上界；规格自己也说只能报「演示召回 + 被挡率」，这两个数一个是 1 个元素的召回，一个是「列出了几个被挡的」，对 VLM 的输出格式极其敏感，结果很难解释。V4（单个动作能不能做 + 为什么）已经覆盖可供性。
4. **测试集审核**：同意从 100 % 人审改成分层抽审，但要给出可写进论文的数：每个任务抽 ~25 条、共 300 条，用户逐条判对错（约 2.5–3 小时）。0 错时 95 % 上界约 1 %；有错就修生成器、重抽。
5. **闭源模型的不确定性**：固定模型快照 id、temperature 0、记录调用日期；在 300 条子集上跑 3 次报标准差；记录每个模型实际收到的图像分辨率（API 会把 1600² 缩小，螺丝可能只剩几个像素——默认用 ROI 裁剪）。开源模型的 JSON 解析失败率单列，报「严格解析」和「宽松解析」两个数。
6. **L1 有一个现成的监督基线不要浪费**：标注辅助用的检测器 v3 / SAM 头 v3 已经在扫描仪上训过。在**训练划分上重训**一次（几个 GPU 小时），和 SAM3 文本提示零样本放一张表——「监督 vs 零样本」是审稿人最想看的 L1 对照。注意现有 v3 权重见过所有台，不能直接拿来评测测试机。

关于新任务 V19 / V7 / V8b / V3b / V20：**只留 V7-cpu**。V19 与 V2 重复；V3b 与 V3 + V10 重复；V8b 和 V20 依赖遮挡顺序，而遮挡顺序有已知的系统性反序（HANDOFF §4.2：压杆 57/57、内存卡扣 714/724 在被扣零件之下），Review 口述也还没开始——用它们出题等于把已知错的层级当真值。

关于微调：同意不进正文承诺。但用户的原话是「可以用来 train 和 evaluate」，正文里没有任何训练实验时，「train」只能写成「提供训练划分」。若第 10 天评测流水线已经稳定，可以加一个最小的 LoRA（一个开源 VLM、V2 + V3 两个任务），否则写进局限。

**划分**：同意现在就定、写进 `Desktop.split`。但不要按 `model_family` 拼写切：拼写变体会把同一平台切到两边；更要紧的是同一个型号族里有不同机箱——p11/p12 显示两件散热器那 8 台横跨 Optiplex 7010 / 7020 / 3010 / 990，而 D02 / D13 也是 7020 却只有一件散热器。按「品牌 + 机箱平台」聚类切（平台可以用每台的零件类别计数 + 边类型做一个简单聚类，人工过目，1 小时）。零样本的结论不依赖划分，但数据集论文需要一个将来可比的划分。

## 4. 两条全局规则改动：数据质量审查

### 4.1 §5 推断 `mounted_on`

**效果比立场稿说的小得多。** 我按立场稿的规则在 r2b 的每个候选对上重算（p4）：上面的零件按规则得到的 `mounted_on` 恰好等于下面的零件，就算作被消掉。

- 消掉 **339 / 2 411**：ram_module→motherboard 126、cpu→motherboard 65、cpu_cooler.fan→motherboard 48、expansion_card.gpu→motherboard 24、cpu_cooler.heatsink→motherboard 20、optical_drive→drive_cage 19、storage_drive.ssd→drive_cage 17、expansion_card.other→motherboard 9、storage_drive.hdd→drive_cage 5、heatsink_fan→motherboard 4、expansion_card.wlan→motherboard 2。
- 剩 **2 072 个、231 个类对**。前几名：ram_module→ram_latch 142（多数是相邻插槽的卡扣，已知层级反序）、drive_cage→ram_latch 103、connector→drive_cage 83、connector→motherboard 76、drive_cage→connector.front_panel 66、drive_cage→screw.motherboard 62、cover→motherboard 58、cpu_cooler.fan→cpu_socket_lever 40……

**对照 taxonomy（`configs/taxonomy.yaml`）：**
- `storage_drive.kind` 只有 `hdd / ssd / unknown`，**没有 `m2`**；副本里 ssd 49、hdd 17，原始名里也没有「m.2 / nvme」（p11）。规则里「m2 / 板载 SSD → motherboard」是死分支。`storage_drive.ssd → motherboard` 22 台的候选一个都消不掉。
- `drive_cage` 每台要么 1 个（34 台）要么 0 个（32 台），「有且唯一」就是「有」；32 台没有硬盘架的机器，硬盘的 `mounted_on` 全空。
- 「光驱装在硬盘架里」是一个物理判断，不是普遍事实（Dell MT 的 5.25 寸光驱位通常是机箱自带的）。那 19 个被消掉的光驱对依赖这个判断，我不建议用规则断言它。
- `motherboard → chassis`、`psu → chassis` 对候选没有任何作用：机箱已经是 `below_fixed`。列表漏了 `case_fan`、`cooler_bracket`、`card_latch`、`psu_latch` 等类，但它们对候选也几乎没影响。
- `cpu_socket_lever`、`ram_latch` 早就是 `parent = motherboard.01` + `attached`，结构理由已经由 `attached_to` 覆盖，再写 `mounted_on` 是重复。

**语义风险。** `mounted_on` 的意思是物理支承。今天的计划器会在 CPU、内存、散热器都还「installed / in_chassis」的状态下把主板拿走（D13 的主板计划就是这样，p2）——零件「悬」在机箱里。日志从来不这样拆（cpu 60/60、ram 107/107 都先于主板拆下），所以演示状态没问题；但任何用计划器模拟出来的状态都是错的。真要把 `mounted_on` 变成数据集的一部分，就要同时定「支承件离开时被支承件怎么办」（连带离开，还是必须先拆），这是状态机的改动，17 天里不该碰。

**它不产生边、不改合法集、不改任何 VLM 标签。** 唯一作用是缩短人工核对清单和发布一个元数据字段。所以写库（推断路径 + `relation_fix` + 重放保留）是用最重的机制做最轻的事。

**建议**：在 `graph_covers.structural_reasons` 里加一张类级「支承」表（cpu、ram_module、cpu_cooler、expansion_card → motherboard），只在导出时生效，候选对上标 `structural: ["rule.supported_by"]`，`instances[].mounted_on` 保持库里的空值，另加一个 `mounted_on_rule` 字段注明是推导的。硬盘 / 光驱 → 硬盘架这一半不做。写库留到 v1.1，那时连同状态机语义一起定。

### 4.2 §6 散热器 / 拉杆

**「没有一台先开拉杆再拆散热器」：成立，但证据很弱。** 副本（p2）：65 台开拉杆的机器，每一个散热器实例都在拉杆打开之前被 `remove` 或 `displace`，0 例外。但间隔是 1–32 步、大多 20 步以上——这是操作员的固定拆法，不是一个「紧」的顺序；任何与演示一致的边都不会产生违规，这句话对一条错的边同样成立。

**真正的证据是像素**（p3，r2b 的 `covers`）：有确认帧的 63 台机器里，**每一台**都是「压在 CPU 上的那件散热器」盖住拉杆（最大 8 720–22 604 像素，多数在 1 万–1.3 万，与拉杆的完整形状同量级）；两件散热器的 8 台里盖住拉杆的**都是散热块**（9 892–11 830 像素），风扇一次也没有直接盖住拉杆。论文和数据卡里应该写这个证据，而不是「0 反例」。

**01b 的诊断要改。** `graph_rules.py` 第 446 行：`FIXED_COVERED_BY = (("cpu", "cpu_cooler"),)`，`_covered_by` 用 `_unique_of_class(instances, "cpu_cooler")` 取散热器（第 557–560 行）。它对任何 kind 都生成——单件 heatsink 的 D22–D26、D29、D32、D33、D35、D36、D49、D62、D63 都有 `covered_by(cpu.01, cpu_cooler.heatsink.01)`；heatsink_fan 的 D27、D28、D30、D31 也有（p3）。**缺的恰好是有两件散热器的 9 台**（D03 D07 D08 D11 D14 D16 D18 D19，以及没拆到 CPU 的 D64），因为不唯一就返回 `None`，一条边都不出，于是 CPU 计划变成两步。01b 说「heatsink 22 台、heatsink_fan 4 台里凡是没有 fan 件的都会这样」不对。

**两件散热器时的结构，数据支持 01b 的说法**：风扇压散热块（8/8 台，13–15 帧，4.8 万–6.6 万像素）、散热块压 CPU（8/8 台，6 300–7 000 像素）；日志里风扇都先于散热块拆（第 14–16 步 vs 第 19–27 步）。

**拉杆那条边不能用 `blocked_by`：**
- `BLOCKED_GATES`：`physical_path` 只挡 `remove` / `displace`，**不挡 `open`**；只有 `tool_access` 或没写模式时才挡全部动词。写成 `blocked_by(lever, cooler, physical_path)`——最自然的写法——这条边对「开拉杆」毫无作用，而且测试不会报错。
- 全库 `blocked_by` 今天是 0 条；模块文档写明 `blocked_by` 留给人工。用规则生成第一批 `blocked_by` 会改变这个约定。
- 现成的类型就是 `covered_by`：挡全部动词，接受状态 `open / removed / displaced`，和「散热器坐在 CPU 上」是同一个物理事实。

**建议的写法**（只改 `_covered_by` 的固定边部分）：
1. 取「压在 CPU 上的散热器」：一件 → 就是它；两件且是 `heatsink + fan` → `heatsink`；其他组合 → 不出边，交 S1 报告（与 `unresolved_fan_owners` 同一种处理）。
2. 生成 `covered_by(cpu, 它)` 和 `covered_by(cpu_socket_lever.*, 它)`（拉杆按类别全部，不要再用 `_unique_of_class`；每台通常一个）。
3. 两件时再加 `covered_by(heatsink, fan)`。
4. 保留 `is_extra` 的排除。

**注意 `displaced` 的含义**：`covered_by` 接受 `displaced`，所以计划器会走「挪开散热器 → 开拉杆」。D45 的日志是第 5 步 `remove` 风扇、第 25 步开拉杆，不冲突；但要用户确认「挪开」对拉杆是否算数（风扇用线吊在旁边时拉杆能不能扳）。如果不算，就用 `blocked_by` + `tool_access`，接受状态只有 removed / displaced / released——差别不大，关键是不要用 `physical_path`。

**还缺的一条**（p12）：那 8 台两件散热器的机器里，硬盘架和光驱压在散热块（中位约 1.9 万 / 2.0 万像素）、CPU（约 4 500 / 5 700）和拉杆（约 7 400 / 8 400）上，这 8 台的日志全部先拆光驱和硬盘架、再拆风扇和散热块（p11）。这是一个平台（横跨 7010 / 7020 / 3010 / 990）的结构，需要用户裁定一条类级规则，例如「有两件散热器的机器：硬盘架、光驱 covered_by 散热块」——或者这 8 台不出 V4 / V6 / V7。

**连带影响**：
- 候选：cooler→lever 实际是 40 + 20 + 4 = **64** 个对（01b 说 56），加上 heatsink→cpu 8、fan→heatsink 8，共 80 个会消失；和 §5 合起来，候选从 2 411 降到约 1 990（−17 %）。候选清单本来就不该是优化目标；该做的是对排名靠前的 10–15 个类对做类级裁定。
- `graph_version` 全变，export-graph / export-vlm 全部重出；65 台第 0 步的合法集合不再有「打开 CPU 拉杆」。
- 导出读的是**库里存的** `relation` 行，所以必须在程序关闭时跑一次写库的 `constraints`（顺便清掉 D63 的 6 条陈旧 `covered_by`）。验证：副本上 `constraints --dry-run --validate` 违规数仍为 24；export-graph 后检查 8 台两件散热器机器的 `plans.cpu.01.length` 不再是 2，且 65 台 `legal_by_step[0]` 里没有 `open cpu_socket_lever`。
