---

## 1. 一句话

我们不额外请人写问答。每一道题都由**已经确认过的标注**加上**拆解日志、状态机和约束图**用程序生成，答案也由程序复核。
所以题量大，答案可追溯，而且每道题都知道它的答案来自哪一层信息。

---

## 2. 想让 VLM 达成什么能力

拆一台电脑，机器人或者辅助系统要会的东西，从低到高分五层。每层对应一组题型。

| 能力层 | 要会什么 | 题型 | 为什么只有我们能出 |
|---|---|---|---|
| L1 感知 | 看出画面里有哪些零件、在哪、处于什么状态 | V1 V2 V8 V14 | 有逐帧确认的实例掩码、状态、可见度。别的数据集也有类似的一层 |
| 变化理解 | 对比前后两帧，说出刚做了什么、有没有变化；从一帧推断已经做过哪些动作 | V3 V12 V10 | 有逐步的动作日志，每一步都对上了帧 |
| L2 可供性 | 现在能不能对某零件做某动作，不能的话被谁挡着 | V4 | 有物理约束图：谁拧住谁、谁插在谁上、谁压着谁 |
| L3 规划 | 下一步做什么；要拿到 CPU 还要做哪些步；一串步骤合不合法，第一处错在哪 | V6 V7 V16 | 约束图加演示顺序，能判断合法与否，而不是只认一个标准答案 |
| 跨视角 / 元认知 | 两台相机拍的是不是同一时刻；这个视角能不能看出某零件的状态，看不出就该说看不出 | V15 V14 | 同一个状态机对应四个视角，可见度不同而答案相同 |

论文的核心卖点在后三层。感知题谁都能出，但「能不能做、被谁挡、下一步、计划对不对、该不该拒答」需要状态机和约束图，
这是我们的标注独有的，而且每多一台机器几乎不增加标注成本。

## 3. 原料：题目从哪些信息里来

| 层 | 内容 | 在库里的位置 |
|---|---|---|
| 图像 | 每一步之后四个视角：扫描仪俯视（主视角，已标）、OAK1、OAK2、RealSense（未标） | `frame`，HF `raw/` |
| 感知标签 | 每帧每个零件的可见掩码和完整形状、类别、跨步一致的实例身份、状态、位置、可见度（看得见 / 部分遮挡 / 完全遮挡 / 画框外 / 太小）、谁挡住谁 | `compiled_mask`、关键帧、层序、两两覆盖 |
| 过程 | 每一步的动词、目标零件、工具、结果；步骤类型（普通、辅助、重摆、重复、失败）；由日志推出的每个零件状态时间线 | `step`、`action`、`state_event` |
| 结构与约束 | 零件关系（装在谁上、拧住谁、插在谁上、线属于谁）；约束边（拧住、连接、卡住、压住、挡住），每条边有来源：规则、像素、你的裁定 | `instance`、`relation`、`cover_ruling` |
| 元数据 | 品牌型号、机箱形态、每个视角的质量等级、平台不相交的划分（12 台测试 / 54 台训练） | `desktop` |

**确定真值原则。** 约束图只记录物理上必要的边，可能不全，所以生成器只把四类「确定」的东西当真值：

1. **演示过的**一定做得了：日志里下一步就是它。
2. **图禁止的**一定做不了：有一条必要边还没满足。
3. **状态上不适用的**一定做不了：已经打开的不能再打开，已经拆走的不能再拆。
4. **真实失败的尝试**：日志里写了失败。

图「允许」但没人演示过的动作只是上界，**从不**当成「能做」的真值。每条可供性和规划题都在标签里写明
`truth_source`，只因像素或你的遮挡裁定才成立的「不行」单独标成 `graph_blocked_pixels`。

## 4. 生成流程，一步一步

1. **冻结。** 导出前把所有容差内的旧行重签，再用 SQLite 备份接口拷一份只读快照（封装快照
   `tda_sealed_20261103.sqlite`）。扫描仪包、零件合照包和 VLM 包都从这同一份快照导出，所以三个包的数字对得上。
2. **逐台、逐视角、逐步出题。** `tda/core/export/vlm.py` 为每台机器建一个上下文：零件表、状态时间线、约束图、
   每个确认帧的可见度表。然后对每个视角的每一步，依次调用 `vlm_tasks.py` 里各题型的生成器。
3. **只从可信的帧读像素。** V1 V2 V8 V14 要读掩码，只对人确认过的帧出题。V3 V4 V6 V7 V10 V12 V16 的答案来自日志、
   状态机和约束图，与视角无关，所以四个视角都出，未标视角只是换一张那台相机的图。V15 不需要掩码。
4. **题面和答案彻底分开。** 每条记录分 `prompt`（模型能看到：题型、不透明的图像 id、问题、选项）和 `label`
   （其余全部：答案、复核方法、证据框、推理链、台号、步号、来源）。图像 id 是加盐哈希，不暴露台号和步号。
5. **问法模板。** 每个题型 5 到 10 种英文问法，按记录 id 的校验和挑一种，所以同一条记录永远是同一种问法，
   而模型又不能靠固定句式猜答案。零件在题面里叫「RAM latch 8」「Fan CPU cooler 1」这样的可读名。
6. **负样本。** 每个是非题都配同等数量的「否」，否例从同一台、同一帧附近按种子打乱后挑，并尽量和正例同动词、
   同类别，避免模型靠「动词 + 类别」就猜出答案。具体每题的负样本见第 5 节。
7. **推理链。** 每条记录带一串结构化的推理步骤（看到什么、想起哪条关系、检查哪个前提），只在标签侧，
   用于审核和以后的训练，不给模型看。
8. **防捷径。** 导出时对每个题型跑五个「只看题面」的分类器（多数类、动词、类别、动词 + 类别、问法模板），
   把最高分写进 `summary.json`，作为「不看图能拿多少分」的上界。V2 按台按类别抽稀，任何答案都不超过该类题量的一半，
   因为原始的状态题 80 % 能靠「这类零件通常是什么状态」猜对。
9. **旁车文件。** 每个视角还导出 `oracle.jsonl`（每台的零件、边、日志，和每张图那一刻的状态表）、
   `masks.jsonl`（确认帧的掩码）和 `summary.json`（计数、跳过的原因、捷径上界）。
10. **冻结评测子集 `eval_v1`。** `vlm_eval_set.py` 固定种子 0，在全部台上分层抽样：是非题每题至少 400 条，
    其他至少 300 条，V6 按开放式 / 选择题成对抽。按答案类别、真值来源、动词、类别等分层，台与台轮流取，
    任何一台不超过该题量的 20 %。两次运行逐字节相同。共 4 300 条。
11. **参照线、自检、审核、人类基线。** 见第 6 节。

## 5. 每个题型

规模是 `data/` 里四个视角的总条数，括号里是扫描仪的条数，最后是 `eval_v1` 的条数（封装后重建的包）。

**V1 看到了哪些零件、在哪**（2 804（2 790）/ 300）
- 输入一张图。答案是每个可见零件的类别和框。
- 评分：零件集合 F1 加框的 IoU。

**V2 某个零件的状态，或某类螺丝还剩几颗**（16 187（16 172）/ 300）
- 例：「In this image, what state is RAM latch 8 in?」答案 `open`。
- 螺丝只问「在 / 已拧下拿走」，不问松紧，因为 2D 图看不出。带 captive 的螺丝（随风扇走的）不问状态。
- 主指标是全部 V2 题（2026-11-03 你定：V2 测的是「现在这里有什么、处于什么状态」）。`eval_v1` 的 V2 已按类别平均抽，
  每类一半是「类别先验猜错」的题，所以靠先验只能对一半左右；先验猜错的那一半单独报一行（`V2-prior-wrong`），作捷径检查。
- 状态从不变化的类别（CPU、主板、内存条等，看得见时永远是「装着」）不加 V2 题，它们在不在由 V1、V8 测。

**V3 两帧之间刚做了什么**（3 936（2 476）/ 300）
- 输入第 k−1 和第 k 帧，答动词、目标、工具。
- 只拧了 captive 螺丝的步不出，因为画面不变。未标视角只问大件的动作。

**V4 现在能不能做这个动作，不能的话被谁挡着**（11 162（5 448）/ 400）
- 例：「Would opening CPU socket lever 1 work right now?」答案「不能，被 CPU 风扇挡着」。
- 正例 = 日志里下一步做的。反例 = 图挡住的（列出全部未满足的边），或状态上不适用的。
- 反例和正例尽量同动词、同类别。评分：能不能的准确率，加阻挡者集合的 F1。

**V6 下一步做什么**（21 826（5 446）/ 600 = 300 对）
- 每帧两条：开放式（主指标）和五选一（副）。
- 开放式按「组等价」判对：演示的动作，或图允许的同动词同类别的兄弟件都算对。比如先拧哪颗散热器螺丝都行。
- 选择题的干扰项两两不同类，并在旁边印出「只看上一步动作」就能选对多少，作为参照。

**V7 要拿出 CPU，还剩哪些步骤**（6 369（1 593）/ 300）
- 只从「CPU 的子计划已经开始、CPU 还在」的帧出题。
- 评分不要求和日志一模一样，看三项：有没有违反必要边、必需的动作召回了多少、最后有没有拿到 CPU。多余的步骤不扣分。

**V8 指出某个零件在哪**（6 441（6 413）/ 300）
- 答一个框。评分：IoU ≥ 0.5，很小的零件只算点在掩码内。

**V10 从一帧推断已经做过哪些动作，进度到哪了**（10 585（2 641）/ 300）
- 答已完成动作的集合，加进度分箱（0–25 %、25–50 % …）。这是历史推断题：只看现在的样子，倒推过去发生了什么。

**V12 两帧之间有没有变化**（1 933（482）/ 400）
- 「没变化」的负样本有两种：重复拍的帧，以及只拧松了 captive 螺丝的步。后者日志里有动作，画面却不变。

**V14 这个视角能不能看出某零件的状态**（4 318，只有扫描仪 / 400）
- 例：「From this view alone, can you tell what state SSD storage drive 1 is in?」
- 完全被挡、在画框外、太小的零件，正确答案是「看不出」。同一帧里看得见和看不见的各取一半，所以多数类正好 50 %。
- 这道题考的是「该拒答时拒答」：被挡住时不应该编一个状态。

**V15 两台相机拍的是不是同一时刻**（30 550（15 294）/ 400）
- 负样本是另一时刻、而且中间有大件变了状态的帧。
- 另一半「cross」（A 视角看不见的零件，在 B 视角是什么状态）需要两个视角都标过，这一版没有出。

**V16 这串步骤能不能执行，第一处错在哪**（21 298（5 314）/ 300）
- 正例是日志的一段后缀。反例是程序篡改过的：替换、挪位、交换，一定违反某条必要边。

**没出的题型。** V5「现在能做的全部动作」退出默认集合，因为合法集合中位数 37 个，又只是上界，没法公平评分。
V9 螺丝头型、V13 失败尝试解释、V17 合照一致性、V18 操作方向是 P1，还没做。

## 6. 怎么保证题目可信、分数可解释

- **题面不泄露答案。** 图像 id 不透明。不允许按证据框裁图，只能不裁，或者用这台这个视角固定的机箱框裁。
  否则 V14 能看出的都有框、看不出的都没框，V8 的框就是答案。
- **参照线。** 每个模型的分数都和这些线放在一起读：
  - **chance**：随机猜。
  - **frequency**：训练台上最常见的答案，模型连这条都过不了，说明什么都没读到。
  - **blind**：只给题不给图，测模板泄露。
  - **protocol prior**：只看上一个演示动作，用留一台的二元模型答 V6 V7 V16，相当于只读日志的文本模型的起点。
  - **state oracle**：把图换成那一刻的结构化状态表，相当于感知满分。
  - **mask overlay**：把确认的掩码按类别涂色叠在图上。它和原图的分差就是「感知的代价」。
- **自检。** `vlm_selfcheck.py` 把标准答案当模型回答喂给评分器，每个题型都必须是 1.0。构建时已在干净环境里跑过，
  收包后先再跑一遍。
- **作者审核。** `eval_v1/audit/` 有 300 条，每题约 25 条，可在浏览器里逐条标「正确 / 错误 / 存疑」，
  汇总给出错误率和 Wilson 95 % 区间（0/300 对应上限 1.3 %）。
- **人类基线。** `vlm_human_sheet.py` 生成不带答案、会计时的作答页，导出后按模型同样的方式打分。
- **已知局限。** 写在包的 README 里：V2 类别偏斜（RAM 卡扣占 72 %）、未标视角的捷径上界偏高、
  光驱支架在题里叫「Optical drive cage N」（评分不接受「optical drive」）、4 台日志有未解目标不出 V10（日志与约束图的矛盾已在 11-03 全部改正）。

## 7. 评测怎么跑

在集群上（`docs/vlm_run_hprc.md`）：

1. 拷包，跑自检，必须全 1.0。
2. 用 `gold` 伪后端走一遍完整链路。
3. 一个开源模型（Qwen3-VL 或 InternVL，vLLM）先跑 100 条试点。
4. 完整的 `eval_v1`：2 个开源模型，每个跑原图和只给题两种输入，scan 再加掩码叠加图。闭源只用 Codex 跑 GPT-6.1 Sol，
   只做你审核的那 300 条（`eval_v1/audit/audit.ids.txt`），跑一次；人类基线也做这 300 条，放附录。
5. 评分器按题型、能力层、问法模板出分，带按台聚类自助的 95 % 区间和每题的捷径上界。

读结果的方式：模型应该在 chance 和 frequency 之上、state oracle 之下。它和 mask overlay 的差距算感知错误，
和 state oracle 的差距算推理错误。

## 8. 新增的次要范围：主视角看不见时，靠之前的动作或其他视角推断

你提出：某一步主视角看不到某个零件时，它的状态其实可以从其他视角或之前的动作推出来。我把它作为**扩展范围**写进计划，
不进主指标。

### 8.1 和 V14 的关系

V14 问的是「**只凭这一帧**能不能看出来」，看不见就该答「看不出」。新题问的是「**结合之前发生过的事**，它现在是什么情况」。
两者不矛盾，但题面必须明确说是哪一种，否则模型会被教成两套相反的规矩。

### 8.2 数据里的实际情况（今晚活库，已确认的扫描仪帧）

| 看不见的情况 | 行数 |
|---|---|
| 状态可问的零件完全被挡、在画框外或太小 | 4 982 |
| 其中从开拆起就一直被压着、还没露出来过 | 4 902 |
| 其中先露出过、后来又被挡住 | 80 |
| 被挡住期间状态发生了变化 | 0 |

**结论：如果直接问「被挡住的零件现在是什么状态」，答案几乎永远是初始状态。** 螺丝还拧着，CPU 还在，卡扣还合着。
模型不看图、不看历史，只凭先验也能答对。这样的题测不出推断能力。

### 8.3 建议的出法：看不见，是还在只是被挡住，还是已经拆走了

真正需要历史推断的是这个区分：画面里看不到 X，它是被别的零件挡着还在机器里，还是前面某一步已经拆走了。
两种情况的标准答案都来自状态机，确定无误。

- **正例**：X 在这一帧完全被挡（还在）。负例：X 在这一帧之前已被拆下。每帧各取一半，多数类 50 %。
- **输入**：当前帧，加上历史。历史给图，比如第一帧加上前几帧，不给文字日志，因为文字日志里直接写着「拆下 X」，等于把答案给了出去。
- **规模**：1 064 帧两种情况都有，按每帧 1:1 配对约 3 500 条，够抽一个 300 到 400 条的子集。
- **答案格式**：`{"present": true/false}`，可选再问「被谁挡着」，用已有的遮挡者标签判分。
- **捷径控制**：按类别平衡，因为螺丝、RAM 卡扣看不见时多半是被挡着，PSU、硬盘看不见时多半是拆走了。
  导出时同样计算只看题面的上界。

### 8.4 跨视角那一半

OAK / RealSense 还没标，现在无法确认 X 在另一个视角里确实看得见。等 OAK 视角确认一批帧以后，
直接用已经设计好、但这一版没出的 V15-cross：A 视角看不见的 X，在 B 视角是什么状态。

### 8.5 工作量与位置

- 历史推断那一半：一个生成器、5 到 10 条问法、评分、测试，约一个工人半天到一天。
- 跨视角那一半：取决于 OAK 的标注进度。
- 在论文里放在扩展任务或附录，作为「物体恒存」的诊断，不进主表的能力层平均。
