## 1. 一句话

我们不额外请人写问答。每一道题都由**已经确认过的标注**加上**拆解日志、状态机和约束图**用程序生成，答案也由程序复核。
所以题量大，答案可追溯，而且每道题都知道它的答案来自哪一层信息。

## 2. 想让 VLM 达成什么能力

拆一台电脑，机器人或者辅助系统要会的东西，按论文图里的分组分三组。

| 分组 | 要会什么 | 题型 | 为什么只有我们能出 |
|---|---|---|---|
| Perception（感知） | V1 Enumeration 有哪些零件、在哪；V8 Grounding 某个零件在哪；V2 State 处于什么状态（含 Screw count 数螺丝，看不见时答「看不出来」）；V15 Cross-view 两台相机是不是同一时刻 | V1 V8 V2 V15 | 有逐帧确认的实例掩码、状态、可见度；同一个状态机对应四个视角 |
| Understanding（理解） | V3 Action 刚做了什么、在哪里变了；V12 State change 有没有变化；V10 Progress 从一帧推断已经做过哪些动作 | V3 V12 V10 | 有逐步的动作日志，每一步都对上了帧 |
| Planning（规划） | V4 Feasibility 现在能不能做、不能的话先要处理什么；V6 Next action 现在能做的全部动作；V7 Plan 拆到某个零件的计划；V16 Plan check 一串步骤能否执行、第一处错在哪 | V4 V6 V7 V16 | 有物理约束图和你给的通用规则，能判断任意顺序合不合法，而不是只认演示的那一个 |

论文的核心卖点在 Planning 和拒答。感知题谁都能出，但「能不能做、被谁挡、现在能做什么、计划对不对、该不该拒答」
需要状态机和约束图，这是我们的标注独有的，而且每多一台机器几乎不增加标注成本。V14 已取消，拒答并入 V2 的 `cannot_tell`。

## 3. 原料：题目从哪些信息里来

| 层 | 内容 | 在库里的位置 |
|---|---|---|
| 图像 | 每一步之后四个视角：扫描仪俯视（主视角，已标）、OAK1、OAK2、RealSense（未标） | `frame`，HF `raw/` |
| 感知标签 | 每帧每个零件的可见掩码和完整形状、类别、跨步一致的实例身份、状态、位置、可见度（看得见 / 部分遮挡 / 完全遮挡 / 画框外 / 太小）、谁挡住谁 | `compiled_mask`、关键帧、层序、两两覆盖 |
| 过程 | 每一步的动词、目标零件、工具、结果；步骤类型（普通、辅助、重摆、重复、失败）；由日志推出的每个零件状态时间线 | `step`、`action`、`state_event` |
| 结构与约束 | 零件关系（装在谁上、拧住谁、插在谁上、线属于谁）；约束边（拧住、连接、卡住、压住、挡住），每条边有来源：规则、像素、你的裁定 | `instance`、`relation`、`cover_ruling` |
| 元数据 | 品牌型号、机箱形态、每个视角的质量等级、平台不相交的划分（12 台测试 / 54 台训练） | `desktop` |

**真值原则（11-04 改了）。** 以前约束图被当成可能不全，只有演示过的才算「能做」。你给出了拆解的通用规则 R1–R17
并裁定了所有遗留情况，现在拆解按 **AND/OR 图**处理，演示的顺序只是其中一条路：

1. 同一类、可互换的动作之间没有先后（插头和插头、内存卡扣和内存卡扣）。
2. 一个动作「现在能做」= 规则和约束图要求的前提都满足、零件看得见，而且：
   - **动态遮挡**：在这一步的扫描仪帧上，没有别的零件压在它上面、盖住它整体形状的 20 % 以上
     （线缆不算，可以拨开；硬盘架盖着插头不算；从不移动的支架不算；例外清单 `configs/occlusion_exceptions.yaml`）。
     按每一步的掩码和层序现算，不存成边；上面的零件一拿走或打开，约束就消失。
   - **掉落零件优先**：机箱里一开始就散落的零件（`attrs.loose`：D43、D60、D65 的机箱风扇，D54 的 SSD 和机箱风扇，D45 的硬盘，D16 的 SSD，

3. V6、V7、V16 都按这个合法动作集判分，不再只认演示的那一个。「不能」都有具体原因，写在 `label.truth_source`：
   `graph_blocked`（规则或边没满足）、`graph_blocked_pixels`（只因像素或你的遮挡裁定成立的边）、`occlusion_blocked`（这一帧被盖住）、
   `loose_first`（先要拿掉落零件）、`state_inapplicable`、`failed_attempt`；「能」是 `demonstrated` 或 `permitted`；V16 的合法序列是 `simulated`（按规则重放过）。
4. **D66** 是多个零件一起拆，不出 V4 / V6 / V7 / V16。

**v7 的约束图**共 3 512 条有效边。按类型：connected_to 1 289、fastened_by 776、covered_by 649、locked_by 372、blocked_by 336、
partner_of 53、is_pre-request_of 35、related_to 2；按来源：rule 3 127、pixels:W3 240、pixels:W4 19、review:covers 33、labelstudio 90、manual 3。

## 4. 生成流程，一步一步

1. **冻结。** 导出前把所有容差内的旧行重签，再用 SQLite 备份接口拷一份只读快照。最终版是 **v7**
   `tda_sealed_20261104_v7.sqlite`（v4 RAM 卡扣按掩码重新配对 → v5 你的约束图裁定和动态遮挡 → v6 D07、D63 重新确认 → v7 D09 复查）。
   VLM 包从 v7 导出；扫描仪包和合照包按 v7 只重导了有变化的台，所以三个包的 key、步骤、状态对得上。
2. **逐台、逐单元、逐步出题。** `tda/core/export/vlm.py` 为每台机器建一个上下文：零件表、状态时间线、约束图、零件组、
   每个确认帧的可见度表和遮挡关系。然后对每个单元的每一步，依次调用 `vlm_tasks.py` 里各题型的生成器。单元有四个：
   相机单元 scan / oak1 / oak2 只出单视角感知题（V1 V2 V8 V15）；`multi` 出动作题（V3 V4 V6 V7 V10 V12 V16）。
   rs 没有自己的记录，它的图只出现在 multi 里；脚本按 manifest 读单元（`tools/vlm_run/pack_units.sh`）。
   - 不画红框的动作题（V3、V6 的三种形式、V10、V12，以及看不到 CPU 时的 V7）一条记录 = 一个时刻所有相机的画面
     （扫描仪、OAK1、OAK2、RealSense 的顺序，没拍到的相机不放），V3 / V12 前后两个时刻，最多 8 张图。
   - 画红框的动作题（V4、V16，以及看得到 CPU 时的 V7）只给画了框的那张扫描仪图。
3. **只从可信的帧读像素。** V1 V2 V8 要读掩码，只对人确认过的帧出题。动作题的答案来自日志、状态机、约束图和这一步扫描仪帧上的遮挡，
   每一步只在 multi 里出一次，真值、证据和标记都来自扫描仪那一帧，其他相机的图只给模型看，不读。V15 不需要掩码。
4. **题面和答案彻底分开。** 每条记录分 `prompt`（模型能看到：题型、不透明的图像 id、问题、选项、标记、图像说明、术语）和 `label`
   （其余全部：答案、复核方法、证据框、推理链、台号、步号、来源）。图像 id 是加盐哈希，不暴露台号和步号。
5. **问法模板。** 每个题型 5 到 10 种英文问法，按记录 id 的校验和挑一种，所以同一条记录永远是同一种问法，
   而模型又不能靠固定句式猜答案。最终的对话格式 id 是 **`chat-v5`**。
   - **不带序号**：题面、选项、答案、推理和审核页都不用序号（不说「RAM latch 8」「connector 3」）。唯一的零件用类别名；
     看得见、画了红框的可以叫 part A；可互换的零件用组名（「the PSU screws」「the connectors」）；看不见的直接说它是什么。
     评分器读的实例 key 只在标签侧（`answer_check.answer_keys`）。
   - **红框标记**：题目点名的每个零件都在扫描仪图上用红色细虚线框（60 % 不透明，画在零件外侧；字母标签放在框外，
     左上角上方，放不下就放下方，绝不压在零件上）圈出，叫「the RAM module outlined in red」或「part A」；V1、V8 不画（框就是答案），
     V2 的数螺丝题按类别问、不画框，V6 的答案和选项直接写动作（「unplug the connectors」「take out the PSU」），也不画框。
     `vlm_to_chat.py` 在图的副本上画框，`--roi view` 裁切时框在 ROI 边缘截断。只给题的变体（blind、state oracle）
     写成「part A (a RAM module)」，所以一条题也不丢。
   - **黄色虚线提示框**（只用在 V3 给提示题）：标准变化区域按中心放大 2.5 倍、每边至少 300 像素，画在前后两张扫描仪图上，不带字母。
   - **零件组**：可互换的零件（一个风扇的螺丝、一根内存条的卡扣、一根线的插头、几根内存条）作为一组来问、来答，
     组 id 是 `<match_class>@<anchor>`。评分器把「the cooler screws」「a CPU cooler screw」这类说法对应到组。
   - **术语表**：每条提示都附上它用到的类别和状态的解释（`tools/vlm_glossary.py`）；每类零件的 displaced 写成具体意思，
     线夹 open = 线已经从夹子里取出。审阅表在 HF `vlm/owner_review/`。
6. **负样本。** 每个是非题都配同等数量的「否」，否例从同一台、同一帧附近按种子打乱后挑，并尽量和正例同动词、
   同类别，避免模型靠「动词 + 类别」就猜出答案。具体每题的负样本见第 5 节。
7. **推理链。** 每条记录带一串结构化的推理步骤（看到什么、想起哪条关系、检查哪个前提），另有 `rationale.text`：
   用图上看得见的物理原因写成的一段话（例如「No: the CPU socket lever still locks the CPU.」，V16 逐步写），不用约束图术语、不带序号。
   这些一起单独导出到 `reasoning/<unit>.jsonl`，每条记录一行 `{id, task, question, answer, reasoning}`
   （scan 81 388、oak1 10 393、oak2 5 068、multi 87 414 行），**只用于以后训练**，绝不给被测模型看。
8. **防捷径。** 导出时对每个题型跑五个「只看题面」的分类器（多数类、动词、类别、动词 + 类别、问法模板），
   把最高分写进 `summary.json`，作为「不看图能拿多少分」的上界。V2 按台按类别抽稀，任何答案都不超过该类题量的一半，
   因为原始的状态题大部分能靠「这类零件通常是什么状态」猜对。全量题库没有平衡（V4 0.853 对多数答案 0.610，V12 0.933 等于多数答案），
   所以评测用平衡过的 `eval_v3`，在它上面只看题面的最好成绩接近多数答案（见第 6 节）。
   **复核。** 除了自检，构建时还用独立的复核器（`tests/vlm_checker.py`）从数据库把每条记录重新推一遍，184 263 条全部一致；
   不变量检查（`tests/vlm_invariants.py`：演示过的动作都可做、被盖住或有掉落零件时没有「能」、前沿上的目标都看得见、每个计划都能重放、
   没有状态事件就没有「变了」、任何文字里都没有 key、序号或图术语）0 违反。
9. **旁车文件。** 每个单元还导出 `oracle.jsonl`（每台的零件、零件组、边、日志，和每张图那一刻的状态表）、
   `masks.jsonl`（确认帧的掩码）和 `summary.json`（计数、跳过的原因、捷径上界）。
10. **冻结评测子集 `eval_v3`。** `vlm_eval_set.py` 固定种子 0，在全部台上分层抽样：是非题（V4、V12、V12.span、V15）每题至少 400 条，
    其他 300 条；V6 按同一帧的开放式 + 选择题成对抽，V6 给约束、V7 给约束各自成桶；V3 按不给提示的题和它的给提示搭档成对抽。
    按答案类别、真值来源、动词、类别、前沿大小、约束类型等分层，台与台轮流取，任何一台不超过该题量的 20 %（每题型 62–66 台）；
    每层里优先取 `eval_v2` 中还存在的 id（`eval_v2` 的 4 298 个 id 里 3 504 个还在，2 776 个被重新抽中）。两次运行逐字节相同。
    共 **5 347 条**：scan 1 097、oak1 137、oak2 66、multi 4 047。按桶：V1 300、V2 300、V3 600（不给提示 + 给提示）、V3.span 300、V4 400、
    V6 447（300 帧的开放题和对应的选择题）、V6.constrained 300、V7 300、V7.constrained 300、V8 300、V10 300、V12 400、V12.span 400、V15 400、V16 300。
    图 8 551 张，23.9 GB；整包 31.8 GB、11 019 个文件。工具拒绝 `eval_v1` / `eval_v2` 的路径。
11. **参照线、自检、审核、人类基线。** 见第 6 节。

## 5. 每个题型

括号里是全量题库的条数（按单元 / 形式）和 `eval_v3` 的条数。全量共 **184 263 条**：scan 81 388、oak1 10 393、oak2 5 068、multi 87 414。

### Perception（感知）

**V1 Enumeration：看到了哪些零件、在哪**（scan 2 790、oak1 14 / `eval_v3` 300）
- 输入一张图。答案是每个可见零件的类别和框 `{"components": [{"class", "bbox"}]}`。
- 评分：按类别匹配，IoU ≥ 0.5 算命中，报 F1（主指标）；另报 COCO 式 IoU 0.50:0.05:0.95 平均（`f1_50_95`）。

**V8 Grounding：指出某个零件在哪**（单框 15 877、多框 13 191（scan），oak1 78 / 300）
- 答一个框（多框形式答一组框），不画红框（框就是答案）。评分：IoU ≥ 0.5 算命中（多框形式按集合 F1），另报 `hit_50_95`。
- V1 / V8 的每个回答都按原坐标和 ×1.25 坐标各算一次取高（有的模型在内部把图缩到约 0.8），记下用了哪种（`frame`），所有模型同一规则。

**V2 State：某个零件的状态，或某类螺丝还剩几颗**（状态 30 730、`cannot_tell` 712、计数 2 794（scan），oak1 113 / 300）
- 例：问红框圈出的那个 RAM 卡扣现在是什么状态，答案 `open`。数螺丝题按类别问，不画框。
- **V14 并入 V2**：一部分帧上会问这个视角看不见的零件（完全被挡、太小、在画框外），正确答案是 `cannot_tell`（「从这张图看不出来」）。
  这考的是「该拒答时拒答」：被挡住时不应该编一个状态。另报 `cannot_tell_accuracy`。
- 螺丝只问「在 / 已拧下拿走」，不问松紧，因为 2D 图看不出。数螺丝：对 1 分，差 1 颗 0.8 分，其余 0 分。
- 主指标是全部 V2 题；`eval_v3` 的 V2 按类别平均抽，每类一半是「类别先验猜错」的题，那一半单独报一行（`V2-prior-wrong`），作捷径检查。
- 全量池偏向 RAM 卡扣（34 349 里 10 815 条）；状态从不变化的类别（CPU、主板、内存条等）几乎没有 V2 题，它们在不在由 V1、V8 测。

**V15 Cross-view：两台相机拍的是不是同一时刻**（scan 15 294、oak1 10 188、oak2 5 068 / 400）
- 负样本是另一时刻、而且中间有大件变了状态的帧。另一半「cross」（A 视角看不见的零件，在 B 视角是什么状态）需要两个视角都标过，这一版没有出。

### Understanding（理解）

**V3 Action：两个时刻之间做了什么**（不给提示 2 331、给提示 2 331、跨步 1 925 / V3 600、V3.span 300）
- **不给提示**（主行 `V3`）：输入前后两个时刻的所有相机画面，答动词、目标、工具，同时给出变化区域 `"region": [x, y, width, height]`
  （扫描仪图的像素）。区域 IoU / 命中是附加行。
- **给提示**（行 `V3-roi`，同一步的搭档题）：图上画黄色虚线提示框，告诉模型变化在框里，只答动作。
- **跨步**（行 `V3-span`）：两个时刻相隔 2–3 步，答这期间做过的全部动作 `{"actions": [...]}`，按动作组算 F1。
- 只认被操作的零件：拿出主板就答「motherboard」，答随它一起走的附着件算错；复合步骤里任一个动作都算对；可互换零件按组算对。

**V12 State change：两个时刻之间有没有变化**（相邻 2 708、隔 2 步 2 652、隔 3 步 2 587 / V12 400、V12.span 400）
- 每对相邻步，加上相隔 2、3 步的，包括没有变化的一对（例如只拧松了 captive 螺丝，日志里有动作，画面却不变）。答 `{"changed"}`。

**V10 Progress：从一个时刻推断已经做过哪些动作，进度到哪了**（2 641 / 300）
- 答已完成动作的集合（和开始了但没做完的），加进度分箱（0–25 %、25–50 % …）。和以前一样，只是去掉了序号。D08、D34、D35、D63 不出。

### Planning（规划）

**V4 Feasibility：现在能不能做这个动作，不能的话先要处理什么**（38 488 / 400）
- 对扫描仪帧上能圈出的每个零件、拆解里用到的每个动词都出题。例：「Would removing the RAM module outlined in red work right now?
  If not, list what is in the way.」
- 「能」= 按规则前提都满足、没被盖住、没有掉落零件。「不能」的原因写成看得见的事实（`answer.reason`）：「两个内存卡扣都还关着」
  「导风罩盖住了内存条」「硬盘架压着它」「先要拿走掉在机箱里的 SSD」；真值来源包括 `occlusion_blocked`、`loose_first`。
- 评分：能不能的准确率（主），阻挡者集合的 F1（附加）。`eval_v3` 的 V4 在每个（动词、类别）格子里平衡。

**V6 Next action：现在能做的全部动作**（开放 2 412、选择 1 380、给约束 1 109 / V6 447、V6.constrained 300）
- 给这个时刻所有相机的图，不画红框，答案和选项直接写动作。
- **开放题**（主行 `V6`）：列出现在所有能做的动作 `{"actions": [...], "why": "<可选>"}`。标准答案是「前沿」：按规则 + 遮挡 + 掉落零件优先，
  现在所有能做、看得见的动作，不是演示的那一个。同类动作合成一组、没有先后（所有插头一组、所有内存卡扣一组、同一零件的螺丝一组），
  按组算精确率 / 召回 / F1。`why` 不判分。
- **选择题**（行 `V6-mc`）：实际上是「现在能拿出哪个零件」，所有选项同一个动词、直接写零件名，恰好一个能做；
  干扰项只用确实做不了的，不出已经做完或没有意义的（例如空槽的卡扣）。只看选项动词的捷径 = 随机水平 0.276。
- **给约束**（行 `V6-constrained`）：提示里多一条文字规则（例如「所有插头拔完之前不能拆 CPU」），按组 F1，另报 `constraint_violation`。

**V7 Plan：拆到某个零件的计划**（不给约束 7 186、给约束 6 752 / V7 300、V7.constrained 300）
- 目标是主要零件（主板、CPU、内存条、电源、硬盘、扩展卡、散热器、支架、机箱风扇），每一步都出。看得到 CPU 时给标框的扫描仪图，否则给所有相机。
- **不给约束**：标准答案是符合规则的最短计划。评分不要求和日志一样：valid（每一步都合法、最后到达目标）、是否到达目标、
  没有违规、必需步骤召回（按规则推出的最少前提，例如目标是 CPU：打开插座拉杆，再取出 CPU）。多余的合法步骤不扣分。
- **给约束**：加一条文字规则，不写插头编号（例如「所有插头都拔掉后才能拆 CPU」），另报 `constraint_kept`、`count_exact`、`count_abs_error`
  （计划里拔的插头数和实际插着的插头数比）。

**V16 Plan check：这串步骤能不能执行，第一处错在哪**（合法 6 600、不合法 6 312 / 300）
- 每个时刻出几条合法和不合法的候选序列（最多 5 步）。合法与否按规则 + 遮挡 + 掉落零件优先**逐步重放**推出（真值来源 `simulated`），
  不因「演示过」算对；不合法的是程序篡改过的（替换、挪位、交换）。答 `{"valid", "first_error_step"}`，推理链逐步写。

**没出的题型。** V5「现在能做的全部动作」不单独导出（它的内容已经是 V6 开放题的前沿）。V9 螺丝头型、V13 失败尝试解释、
V17 合照一致性、V18 操作方向是 P1，还没做。

## 6. 怎么保证题目可信、分数可解释

- **题面不泄露答案。** 图像 id 不透明。不允许按证据框裁图，只能不裁，或者用这台这个视角固定的机箱框裁。
  否则 V2 看得见的零件都有框、`cannot_tell` 的几乎都没框，V8 的框就是答案。
- **解析和区间。** 回答按 strict（整段一个 JSON）和 lenient（文中最后一个完整 JSON）两种解析，两种失败率都报；
  区间是按台聚类的自助法 95 % 区间（1 000 次，种子 0）。
- **参照线。** 每个模型的分数都和这些线放在一起读：
  - **chance**：随机猜。
  - **frequency**：训练台上最常见的答案，模型连这条都过不了，说明什么都没读到。
  - **blind**：只给题不给图，测模板泄露（红框措辞改成「part A (a RAM module)」，不丢题）。
  - **protocol prior**：只看上一个演示动作，用留一台的二元模型答 V6 V7 V16，相当于只读日志的文本模型的起点。
  - **state oracle**：把图换成那一刻的结构化状态表，相当于感知满分（没有 V2 `cannot_tell` 题，因为状态表的可见度一栏就是答案）。
  - **mask overlay**：把确认的掩码按类别涂色叠在图上（只有扫描仪帧有掩码；multi 只涂扫描仪那几张）。可答的：scan 1 097 条里 598 条，
    multi 4 047 条全部，oak1 / oak2 0 条。它和原图的分差就是「感知的代价」。
- **只看题面的捷径（`eval_v3`，最好的纯文本分类器 vs 多数答案）**：V2 0.508 vs 0.272，V3 0.225 vs 0.19，V4 0.5525 vs 0.5225，V12 0.521 vs 0.5，
  V15 0.535 vs 0.5，V16 0.63 vs 0.5；V6 选择题只看选项动词 = 随机水平 0.276。
- **自检和复核。** `vlm_selfcheck.py` 把标准答案当模型回答喂给评分器，184 263 条全部 1.0；独立复核器全部一致，不变量 0 违反。
  收包后先再跑一遍自检。
- **作者审核。** `eval_v3/audit/` 有 300 条，来自 64 台（multi 225、scan 65、oak1 8、oak2 2）：
  V1、V2、V3 不给提示、V3 跨步、V4、V6 开放 / 选择 / 给约束、V7 不给约束 / 给约束、V8、V10 每桶 19 条，V12 36 条（含跨步），V15、V16 各 18 条；
  其中 142 条沿用自 `eval_v2` 的审核样本。打开 `audit.sheet.b01…b06.html` 在浏览器里逐条标「正确 / 错误 / 存疑」：
  每条先显示模型看到的图（红框、黄色提示框照转换器的画法），证据框和答案框放在「显示审核框」开关后面，绝不给模型看。
  只审程序推出来的答案：V1、V8 的真值就是确认过的掩码，不审，要审的是 262 条；其中 12 个 V2 结论沿用第一轮
  （HF `vlm/owner_review/eval_v3_audit_carried.csv`），实际还剩 250 条。汇总给出错误率和 Wilson 95 % 区间（0/262 对应上限约 1.4 %）。
  闭源模型只答这 300 条，答一次。
- **人类基线（已从计划里拿掉，暂缓）。** `vlm_human_sheet.py` 生成不带答案、会计时的作答页，导出后按模型同样的方式打分。
- **已知局限。** 写在包的 README 里：V2 类别偏斜（全量 34 349 条里 RAM 卡扣 10 815 条，约 31 %；`eval_v3` 按类别平均抽）、
  OAK 单元主要只有 V15（加上 D01 oak1 确认过的几帧），rs 没有记录；D08、D34、D35、D63 不出 V10；D66 不出 V4 / V6 / V7 / V16；
  `failed_attempt` 只有 2 条 V4；全量题库没有平衡，所以只看题面的上界在全量上偏高（V4 0.853，V12 0.933），评测用平衡过的 `eval_v3`。

## 8. 新增的次要范围：主视角看不见时，靠之前的动作或其他视角推断

你提出：某一步主视角看不到某个零件时，它的状态其实可以从其他视角或之前的动作推出来。我把它作为**扩展范围**写进计划，
不进主指标。

### 8.1 和 V2 `cannot_tell` 的关系

V2 的 `cannot_tell`（原来的 V14）问的是「**只凭这一帧**能不能看出来」，看不见就该答「看不出」。新题问的是「**结合之前发生过的事**，它现在是什么情况」。
两者不矛盾，但题面必须明确说是哪一种，否则模型会被教成两套相反的规矩。

### 8.2 数据里的实际情况（11-02 晚的活库，已确认的扫描仪帧；v3 封装前测的，真要做时重测）

| 看不见的情况 | 行数 |
|---|---|
| 状态可问的零件完全被挡、在画框外或太小 | 4 982 |
| 其中从开拆起就一直被压着、还没露出来过 | 4 902 |
| 其中先露出过、后来又被挡住 | 80 |
| 被挡住期间状态发生了变化 | 0 |

**结论：如果直接问「被挡住的零件现在是什么状态」，答案几乎永远是初始状态。** 螺丝还拧着，CPU 还在，卡扣还合着。
模型不看图、不看历史，只凭先验也能答对。这样的题测不出推断能力。

### 8.3 建议的出法：看不见，是还在只是被挡住，还是已经拆走了

真正需要历史推断的是这个区分：画面里看不到 X，它是被别的零件挡着还在机器里，还是前面某一步已经拆走了。
两种情况的标准答案都来自状态机，确定无误。

- **正例**：X 在这一帧完全被挡（还在）。负例：X 在这一帧之前已被拆下。每帧各取一半，多数类 50 %。
- **输入**：当前帧，加上历史。历史给图，比如第一帧加上前几帧，不给文字日志，因为文字日志里直接写着「拆下 X」，等于把答案给了出去。
- **规模**：1 064 帧两种情况都有，按每帧 1:1 配对约 3 500 条，够抽一个 300 到 400 条的子集。
- **答案格式**：`{"present": true/false}`，可选再问「被谁挡着」，用已有的遮挡者标签判分。
- **捷径控制**：按类别平衡，因为螺丝、RAM 卡扣看不见时多半是被挡着，PSU、硬盘看不见时多半是拆走了。
  导出时同样计算只看题面的上界。

### 8.4 跨视角那一半

OAK / RealSense 还没标，现在无法确认 X 在另一个视角里确实看得见。等 OAK 视角确认一批帧以后，
直接用已经设计好、但这一版没出的 V15-cross：A 视角看不见的 X，在 B 视角是什么状态。

### 8.5 工作量与位置

- 历史推断那一半：一个生成器、5 到 10 条问法、评分、测试，约一个工人半天到一天。
- 跨视角那一半：取决于 OAK 的标注进度。
- 在论文里放在扩展任务或附录，作为「物体恒存」的诊断，不进主表的能力层平均。
